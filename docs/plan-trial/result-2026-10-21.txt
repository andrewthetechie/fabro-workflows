Plan trial (#25) — result, 2026-10-21
=====================================

Question (docs/plan-trial/README.md): replace `improve` on the coder box with `plan` on
hosted glm-5.3, which does improve's job and also writes the edit plan the coder follows.
Arms split per run by issue parity in `route_lane`.

Window: 2026-10-14 to 2026-10-21, UTC (inclusive dates; every run dispatched in it).
Measured 2026-10-21 ~16:00Z, before any of the trial's code was deleted.

VERDICT: option 1. `plan` wins. `improve` is deleted, `plan` is kept and its timeout is
re-derived from this window (see *The timeout*, below). Recorded in ADR 0030, which reverses
ADR 0011's 2026-09-24 decline of a hosted planner.

The three numbers that decided it
---------------------------------
1. Coder box-minutes per task, 10.9 for `plan` against 12.3 for `improve` pooled (-12%),
   and 10.7 against 11.2 standardized over repo x coder pool (-5%; see *Standardized
   comparison*, below). This is the number the trial exists to move: the box is the scarce
   resource (ADR 0007). Add the planner itself and the box's whole cost per task is 10.9
   against 21.1: `improve` spent another 8.8 box-minutes per task (1278 over 145) that
   `plan` spends off the box.
2. Rework visits per task, 0.14 against 0.19 pooled and 0.13 against 0.16 standardized
   (hosted rework tiers 0.05 against 0.06), and coder + rework minutes per task, 12.3
   against 14.0 pooled and 11.9 against 12.7 standardized. Less reworking follows the plan.
3. Non-architecture merges, 29 of 60 (48%) against 25 of 59 (42%); all PRs 30 of 70 (43%)
   against 28 of 68 (41%). Same direction, inside a 50-PR-per-arm noise band the README
   already said can only show a ~15-point gap.

Two secondary readings also favour `plan`: the Refuter's first verdict passed 37 of 69
against 33 of 66, and the planner costs the box nothing at all (0 planner box-minutes
against 1278, i.e. 21.3 box-hours) while using fewer hosted tokens per run (0.13M input /
1.33M cache-read / 37k output against 0.32M / 1.61M / 26k).

Two readings favour `improve`, both recorded in *Where `improve` looked better*.

How this was measured
---------------------
Read-only on the host. No event export to the Mac; the only events read were streamed on
the host through `jq` filters (two runs, for the timeout derivation). The measurement
scripts were passed to the container on stdin and are not committed, because the trial's
code they called is being deleted in this same close; what they ran is written out here.

Confounds seen
--------------
- Repository and pool mix. The plan arm drew more lawncare-saas on coders-b (10 runs / 30
  tasks against 7 / 20) and more womens-fantasy-sports on coders-a (26 / 64 against 21 /
  41); lawncare-saas is the slowest repo per task and womens-fantasy-sports on coders-c the
  fastest. The per-task numbers are therefore read per stratum and standardized (above).
- Task size per PR. The plan arm carried 2.60 tasks per PR against 2.13, and 6.07 tasks per
  merge against 5.18. This is the confound behind the throughput row: lease hours per task
  are 1.02 for `plan` and 1.07 for `improve` (plan better), but lease hours per merged PR
  are 6.2 against 5.5 (plan worse) because plan's PRs averaged more tasks each. The
  throughput row is mix, not the planner.
- The window's shared changes. Task validation on womens-fantasy-sports (2026-10-15
  01:11:50Z), the Refuter-evidence fix (#40, 10-15), coders-a's model swap (2026-10-18
  04:53Z) and the prompt rewrite `9b2b7cb` (2026-10-18 06:59Z) all landed inside the
  window and hit both arms. They are why the stratum, not the calendar, is the unit above,
  and they make per-visit `validate` numbers incomparable across those dates (the README's
  2026-10-14 cross-trial note).
- writers-app#1040 (run 01M4X9JDEAADWWE64WFXZSVDYA, coders-d) alone is 7 of the plan arm's
  10 `validate` failures, over 13 visits. The other 3 are 2 on womens-fantasy-sports#1578
  and 1 on #1680. The improve arm's 3 failures are 2 on #1675 and 1 on #1515. So `0.05
  against 0.02` per task is one bad PR against two small ones, not a planner property.
- The plan disposition answer from #25 (comment 6305216639) stands for this window: `plan`
  returned `ready` 182 times, `improve` returned `ready` 145, `redundant` 3 and `invalid`
  1. The 3 redundants are one run (01M5CX023VKP67M9Y7R10E5YNG, writers-app#1089) re-reporting
  a duplicate issue, and were correct; the 1 invalid is the gate's verdict after `improve`
  failed to submit twice (run 01M59QSAH8S0XRPC28ZJX60ASR, womens-fantasy-sports#2163: two
  `improve` visits, zero `plan` visits). Both are `improve`-arm runs. Nothing in the plan
  arm's checkpoints marked an already-done task `ready`. `plan` was still never tested on
  an overlap, because issue parity never gave it one.

Where `improve` looked better
-----------------------------
- `validate` failures per task: 0.02 against 0.05, which is #1040 (above).
- Box-hours per merged PR: 5.5 against 6.2, which is task mix (above).

Nothing in the window says `improve` plans better. It says the plan arm's PRs carried more
tasks and that one plan-arm PR had a bad validate history. On the share of PRs the operator
had to touch, `plan` is ahead (10 of 70, 14%, against 14 of 68, 21%), a 4-PR difference that
is recorded and not read.

The timeout
-----------
Measured on this node, this window (n=182 successful `plan` visits over 79 runs; the
terminated hang below is excluded, and 1 of 183 visits hit the cap):

    per visit minutes: p50 4.7   p90 7.5   max 12.7
    per run minutes:   p50 7.3   p90 27.7  max 63.2   (a run plans up to 8 tasks)
    stage timeouts:    1 of 183 visits; failures: transient_infra 1
    improve, same window, for the peer: per visit p50 6.4, p90 15.9, max 19.7

The one stall: run 01M58C5ZZC0GMCT743DDA2EWK7 entered `plan` at 20:51:57Z on 2026-10-18,
`stage.failed` at 21:11:57Z -- exactly the 20m timeout, no `agent.llm` output in the last
minutes -- then `stage.retrying`, a second attempt at 21:12:02Z that completed at 21:20:10Z
(8.1 min) and wrote `ready`. `max_retries=1` recovered it. The collector records only the
successful attempt's 8.1 min in `run_stage_stats`, so this window's planner minutes
under-count stalls by however long each timed-out attempt ran; the `Planner timeouts` row,
not the minutes, is the stall count.

Excluded outlier: run 01M5B0G5ZVJ2X5X5KZZACGKFRK (writers-app#1054, coders-d) records one
`plan` visit of 25,742,196 ms (429 min) with `timeouts 0` and `failures {}`. Its events end
at 21:30:40Z on 2026-10-19 and the run ends `failed/terminated` at 04:33:54Z on 10-20, with
no stage failure, because the 10-19 disk fill killed the worker and the operator's fabro
restart failed the phantom run (`~/.fabro-deploy/docs/FABRO-DEPLOYMENT-LOG.md`,
"2026-10-20 ~04:00-04:40Z"). That is infrastructure, not planner time: it is a hung
process, and it is the reason the timeout cannot be read from `wall_ms` alone.

Choice: **keep `timeout="20m"`, now measured rather than peer-derived**, with
`max_retries=1` unchanged.

- 20m is 1.6x the slowest successful visit in the window and 2.7x p90. The review nodes'
  house rule is 2.3x the slowest observed execution, which here would be 29m; that
  headroom is not worth buying on this node, because `plan` has exactly one failure mode --
  a provider stall that produces nothing -- and every minute of the timeout is a minute of
  the run's lease and of z.ai's 3 concurrent sessions (ADR 0003).
- 15m (the review peers) would leave 2.3 minutes over the observed max, on 1 visit in 182
  above 12 minutes. Too close.
- The measured stall already ends at 20m and its retry costs 8.1m, so a stall costs the run
  ~28m of lease. Under 20m that bounded total is what the operator pays, and it is under
  `improve`'s 45m single attempt.

The graph's comment above `plan` carries these numbers.
