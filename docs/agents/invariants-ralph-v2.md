# Invariants: ralph-v2

Read before changing `.fabro/workflows/ralph-v2/`, its prompts, its `workflow.toml`, or its copies
of `ralph`'s nodes (ADR 0034, `docs/plans/ralph-v2/`).

`docs/agents/invariants-ralph.md` holds for every node `R10_V2_COPIES` lists in
`ops/check-graph-invariants.py`: each one is `ralph`'s node, byte for byte or with its one
recorded replacement, so a rule there about one of those nodes is a rule here too, except where
this file says otherwise. Read that file first. This file holds what is particular to
`ralph-v2`: the per-Task loop, the issue-level round's order, and the package. The graph,
stylesheet and hook rules in `invariants-graph.md` apply as well.

The two nodes `R10_V2_OWN` names, `pick` and `record`, are `ralph-v2`'s own rewrites of `ralph`'s
and R10 compares neither. Everything else that is new is the ten Task-loop nodes: R19 holds the
two Task reviewers, their check nodes and their twins, and the gate tests in
`ops/gate_tests/test_ralph_v2.py` hold all ten.

## The Task list

| Rule | What happens otherwise |
|---|---|
| `/tmp/fabro/tasks.json` is written ONLY by command nodes: `plan_gate` (the first eight Tasks), `pick` (the six-missed block and the review recovery), `task_plan_gate` (`plan_type`), `record`, `task_review_prep` (the no-diff pass), `task_review_gate`, `refute_gate`, `review_gate`, `local_review_gate`, `final_check` and `ci_task`. No agent may write it, and the Iteration prompt says so | An agent that adds, reorders or passes its own Task decides what the loop does next, and `record`'s pass accounting is computed from a file the agent graded itself. The `io-guard` hook seals it from the planner and both Task reviewers too. |
| `reviewing` is a pre-PR Task whose mechanical check passed and whose box review has not decided yet. `record` sets it and publishes `review_due=true`; `task_review_gate` is the only node that sends it to `open` or `blocked`, and only three nodes pass it: the gate, `task_review_prep` (a Task with no diff, or one over 2,000,000 bytes, with the reason in `review_note`) and `pick`'s recovery, below | A status written anywhere else is a review that did not happen: the Task passes with nobody reading its diff, or it sits in the one state `pick` recovers. `reviewing` is also the recovery's only signal, so a Task left in it means the gate died, never that a reviewer is thinking. |
| `pick`'s Iteration cap is tested only when the Task's `reviews` is 0. The pre-PR cap is `min(24, 3 × the Task list)` and a rework Iteration counts in `rework_iterations`, not `iterations` | A Task whose last allowed Iteration passed could never get the rework its review asked for: the review would be able to reject work the run has no budget to fix (P9, E10). |
| `pick` publishes `task_step` (`plan`, `work` or `none`) and `record` publishes `review_due` (`true` exactly when it set `reviewing`) on EVERY path, each from a value this visit computed | A stale key routes the visit after it: `pick`'s two work edges read `task_step`, so a leftover `plan` re-plans a planned Task and a leftover `work` skips the plan; a `review_due` left true sends an Iteration that failed the mechanical check to the reviewers. |
| Every pre-PR Iteration writes `git diff --no-renames "$(cat task_base_sha)" HEAD` to `task_review/state/patches/<id>/<NNN>.patch`, `NNN` the number of patches there plus one, three digits (P2). An empty diff writes no file, and a failed diff writes none and one stderr line. `task_base_sha` is written AFTER the Task's merge into `main`: by `pick` on a clean merge, by `resolve_merge_gate` when the resolver had to redo it | The reviewers read the concatenation of the patches, so one missing patch is a piece of the Task they never see. A base taken before the merge carries the mainline's own changes in the patch, and the reviewers report the rest of the factory's work as this Task's defects. |
| The `## Goals` render of `task-context.md` is one jq program text, present verbatim in `pick` and in `task_plan_gate`, and a gate test compares the two | `task_plan_gate` renders the dossier the accepted plan implies and `pick` renders the one the coder works from. A drift means the planner refreshes a dossier the Iteration never sees, and the goals the coder is judged on are not the goals that were validated. |
| `task_plan_gate` publishes `task_plan_route`, `task_plan_type`, `task_plan_goals` and `task_plan_edges`, and NEVER `rung` | `rung` is `pick`'s alone and the three `excerpts` edges to the Iteration tiers read it from the context. A second publisher would have to agree with `pick` on every path forever, and its natural value, `0`, sends a planned Task to `stop_reason` with `loop=work`. |

## The Task review

| Rule | What happens otherwise |
|---|---|
| `max_retries=0` on `task_plan`, `task_refute`, `task_review`, `task_refute_fb` and `task_review_fb`: their gate or check node owns the retry (P8). R19 holds the two Task reviewers and their twins: it fails the graph when one of those four sets a retry, when a check node or a hosted twin is missing, when the twin resolves to a coder pool or a `coders-*` literal, when the stage or the twin has an edge that is not to its check, or when a check has no unconditional edge that is not a loop back. `task_plan`'s `max_retries=0` is checked by nothing offline | One C4 "try" would be two sessions, and E13's three tries become six or nine (A3). A twin on a coder pool claims a box the run does not lease. An edge past the check routes a missing result as if a reviewer had read the diff. The check's unconditional edge is the escape a crashed check takes. |
| `stage-end` covers a session that ended `succeeded` with nothing written: it re-runs it twice, and when its two re-runs are spent the check goes to the hosted twin without counting a try. The check counts only timeouts and failures (A3). The hooks name `task_plan`, `task_refute` and `task_review` beside v1's six (`iterate_t1`, `plan`, `plan_review`, `local_standards`, `local_spec`, `learn`); the two `_fb` twins are hosted and are not in the list | Counting the stage's re-runs and the check's tries both would allow nine sessions for one review. A box reviewer left out of the list ends the stage with no result, and the check pays a hosted session for a box that was about to work. |
| The receipt rule: `_io.stage` is the stage or its `_fb` twin, and `_io.visit` is non-empty and equals `.io/stage.json`'s. The check node's table is the only retry path — served: write `box` or `fallback` to `state/<K>.served`, `next=done`; invalid with `state/<K>.fb`: write `missed`, delete the result; invalid with `stage-end`'s mark holding this visit: create `fb`, `next=fallback`; otherwise one try added, `next=retry`, and at 3 the `fb` file; below 3 a box-health wait (40 polls, 15 s apart, a 5 s curl) and not healthy in ten minutes means `fallback` | A hand-written result, or the twin's result for an earlier visit, is read as this round's. A reviewer that ended with nothing is read as a reviewer that found nothing, which passes the Task. |
| `state/<K>.served` is `task_review_gate`'s ONLY proof of who served a review: `box`, `fallback`, `missed`, or nothing at all when the check crashed, which the gate publishes as `missed`. The gate never re-derives a served reviewer from the result file | The gate would trust a file it did not see the check accept, so a stale or twin-written result counts as a review. The same three words are what the scorecard counts, and a reviewer that rejected the work is none of them (E11). |
| Both reviewers run every round: `record -> task_review_prep` on every pre-PR pass, `task_review_prep -> task_refute` on every visit that did not pass the Task for want of a diff, `task_refute_check -> task_review` on every visit. There is no size trigger and no sampling (E7), and both report everything they can ground (E8) | The Refuter and the review arrive one finding at a time — 64 of 86 failing Refuter visits in the baseline raised exactly one blocker — and a Task's four reviews are spent on four findings instead of one rework taking all of them. |
| The Sealed lists are the manifest's, not the prompts'. The Task reviewers may not read each other's `out/` file, `task_review/state/`, the stored plan, `tasks.json`, `current_task.json`, `task-context.md`, `task-code.md`, `progress.md`, `iteration.json`, `task_list.json`, `feedback/`, `plan_review/`, `local_review/` or `review/`; `task_plan` may not read `task_review/`, `task_plans/`, `tasks.json`, `task_list.json`, `feedback/`, `plan_review/`, `local_review/` or `review/`; the hosted and local reviewers add `task_review/`, `task_plans/` and `task_plan.json` to v1's list; `learn`, `resolve_merge` and `resolve_base` add `task_review/` and `task_plans/`. The Refuter alone adds `review/standards.json` and `review/spec.json`. `io-guard`'s matcher is v1's without `iterate_t4`, plus `task_plan`, `task_refute`, `task_refute_fb`, `task_review` and `task_review_fb` | A reviewer that read its twin's result is not a second reviewer (P5). The Refuter's two additions are this round's hosted results, which in v2 run before it: a Refuter that read them would restate the reviews instead of proving the work undone. A stage missing from the matcher is unguarded and silent. |
| An Iteration is sealed from `task_review/` and `task_plans/` in all three `iterate_tN`, and `io-guard` matches them | The session that must be judged could read the reviewers' findings and write their result: it would grade itself. It could also rewrite the stored plan it is measured against. |
| The evidence rule, applied by `record` to a dispute and by the gate to every finding: a `path:N` whose path is a file in the checkout (`[A-Za-z0-9_./-]+:[0-9]+`), or a non-empty span in backticks. A dispute survives only when its own reviewer reports it `upheld` with `new_evidence` that passes the rule and whose normalized text differs from the original; anything else withdraws it, and the withdrawn pair goes to `state/dropped/<id>.json`, where a repeat is dropped this round and every later one (E12) | A reviewer that says "I could not find it" without a path becomes a Task nobody can work, and a dispute with no evidence becomes a veto on any finding the coder dislikes. An unchanged repeat costs a round and tells the coder nothing new, so the withdrawal has to be remembered or the same finding returns every round. |
| A review never touches `misses`, so a rejected review never climbs the ladder (E11): `record` is the only node that counts a miss, from the mechanical check, and `pick`'s rung comes from `1 + misses / 2` | A reviewer's opinion would buy the Task `glm-5.3-flash` and then `kimi-for-coding`, and E16's ladder would measure the reviewers instead of the coder. |
| Recovery goes through `pick`. A `task_review_gate` that crashes publishes nothing and leaves the Task `reviewing`; its unconditional edge into `pick` finds that Task, adds one to `task_review/state/recovers/<id>` and re-enters the review, three times, then passes it with `review_note` = `the Task review did not finish` | A Task whose gate died would need a human to finish the run, and the run would stop on a stage nobody can debug from the PR. The counter is safe because only failures return to `pick` as `reviewing`; a normal rework is an `open` Task. |
| The Task review is not a copy of the Refuter: two schemas, two stages, two files, always in this order, and neither sees the other's result (P5). `task_refute` and `task_review` are new nodes, in neither `R10_V2_COPIES` nor `R10_V2_OWN`, so R19 and the gate tests hold them. The two check nodes are one program with three names changed, and a gate test compares them | An R10 row would hold a Task reviewer to `ralph`'s issue-level Refuter, which is a different prompt and job. Two check nodes that drifted would take different paths through C4 for the same failure, and one of the two reviewers would retry where the other misses. |

## The issue-level round (E14, P6)

| Rule | What happens otherwise |
|---|---|
| The round is v1's nodes in E14's order: `local_review_prep` / `local_review_gate` -> `review_prep` -> `standards` -> `spec` -> `refute_prep` -> `refute` -> `refute_gate` -> `review_gate`. `review_prep` tests `/tmp/fabro/loop_exhausted` FIRST: it deletes `review/fix_result.json`, publishes `review_run_standards=false` and `review_run_spec=false`, and exits 0 | v1 reviews only after the Refuter passes, so a round spends itself on one side: a review error then costs a whole extra round, and an exhausted run with a diff over 2 MB reaches `review_prep` and ends at `mark_stuck` instead of `open_pr` (P6). v1's order is safe there only because an exhausted run never reaches its `review_prep`. |
| `refute_gate`'s exhausted reason keeps its opening words and appends the Task's `block_reason`: `not passed when the loop ran out: <block_reason>`, in `fix_result.json`'s `not_fixed`. `open_pr`'s *Unmet criteria* line appends the same to the Task's status | A Task blocked by its box review renders in the PR as a Task that merely ran out, and the one sentence a person reads about the hold does not say why. |
| `resolve_merge` runs on the box: `class="merge-resolve"`, `timeout="60m"`, `max_retries=1`, `box: true` in the Stage manifest, and its prompt is R10's. `resolve_merge_gate` is `ralph`'s node with no replacement | R13 fails a box stage whose class resolves to a hosted model, and a box-classed stage the manifest calls hosted runs with no claim and steals a box. The 60m is reasoned, not measured (v1's 30m was taken on `glm-5.3`): task 13 re-times it. |

## The package

| Rule | What happens otherwise |
|---|---|
| A dispatch carries the entrypoint's package and `workflows/_shared/` and nothing else (`package_paths`, ralph-v2 task 01). `ops/check-payload.py` holds every package under 1,500,000 bytes — `ralph-v2` is 700,619 — and refuses a file over 512 KiB. The generated manifest stays under 120,000 bytes, rule 7 of `ops/fabro-io-manifest.py`; `ralph-v2`'s is 75,377. The graph stays under 350,000 bytes (P14); it is 234,036 | The server refuses a version over 2 MiB, and that refusal stops **every** workflow's dispatch, not the package that grew (A1). The manifest is one environment string and Linux caps one at 131,072 bytes: a package past it fails every stage start of every run. |
