# Invariants: backlog and the issue queue

Read before changing `backlog`'s issue selection, queue labels, Child issues (`_shared/triage/`'s `apply_split`), `open_pr`/`open_pr_prep`, or the rescue gate.

Every rule here passes `fabro validate` and fails at runtime, usually silently. Each one cost a live incident or was found before it could. Moved verbatim from `AGENTS.md` on 2026-10-09; the area files are siblings of this one.

## The fast lane (ADR 0023)

| Rule | What happens otherwise |
|---|---|
| `route_lane` writes `lane=fast` only when `issue.json` labels contain `fast-path` exactly, and writes the one-task `tasks.json` itself | A malformed file must exit 1 to `rescue_brief`; guessing a lane would send a standard issue down the short path. |
| `next_task` prints `rebase_failed:false` on its done branch, and every standard edge it shares with a fast edge carries `lane!=fast` | Two matching conditional edges: the cascade picks by weight, not by what you meant. |
| `rework_router` round 6: `demote_lane` (lane=fast) and `drop_followup` (task_exempt, lane!=fast) are exclusive | The fast task would be dropped instead of demoted. |
| `demote_lane` removes `fast-path` first, then adds `agent`, then comments | Adding `agent` first would leave an issue the scheduler can pick up again in the fast lane. |
| `apply_split` never copies `fast-path` to a child | A split child would skip decomposition it needs. |
| `pr_handoff` writes `queue` only for the fast lane, no `remainder_kind`, inside 200 lines / 10 files | Over the ceiling the PR waits for CI like any other. |

## The planner (`plan`, ADR 0030)

The plan trial (#25) chose `plan` and deleted `improve` on 2026-10-21
(`docs/plan-trial/result-2026-10-21.txt`). These are the rules the trial left behind.

| Rule | What happens otherwise |
|---|---|
| `plan` is the standard lane's only planner and `next_task -> plan` is unconditional; every other edge out of `next_task` and every other route into `plan` is conditional | Two matching conditional edges: the cascade picks by weight, not by what you meant. `next_task` writes `tasks_done` and `rebase_failed` on every branch, and `route_lane` writes `lane`, which is what makes the conditional ones exclusive. Covered by the gate tests (`ops/gate_tests/`). |
| Every stage that can hand a task to a planner reaches `plan`: `next_task`, `resolve_merge_gate` (`merge_return=task && lane!=fast`) and `improve_gate`'s retry (`outcome=failed`) | A retry or a resolved mainline merge would fall through to the node's unconditional edge, `rescue_brief`, and a run that only needed a second planning pass waits at the rescue gate. `fabro validate` rejects an edge to a deleted node, but not one that routes to the wrong live node. Covered by the gate tests (`ops/gate_tests/`) (parsed edges). |
| `plan` writes `/tmp/fabro/improve_result.json` (schema `improve_result`) to `improve_gate`, and the gate's `improve_result.json`, `improve_attempts`, `improve_touched_tree` and `excerpts` keep their names | Renaming them is churn across the Stage manifest, the schema, the receipt check, the split guards and the task budget, for no behaviour change. The names are the only thing the node and the gate share. |
| `.plan` resolves to `glm-5.3` and never to `{{ inputs.coder_pool }}` | Planning goes back onto the run's leased box, the cost ADR 0030 removed (`improve` spent 8.8 box-minutes a task there), and the 20m timeout was measured on `glm-5.3`, not on a box. Nothing fails; the box is simply busy again. |
| `plan`'s timeout is measured on this node (`timeout="20m"`, 1.6x the slowest visit in the trial window) and moving `.plan` to a different model voids it | A measurement-derived timeout whose subject changed is not a measurement; `improve` burned two 900s attempts that way in run 01M321VB0DC4N187GHA88RM0QB. |

`_shared/triage/` has its own `improve` and `plan` stages (`issue-triage` and `arch-review`
import that phase). They are different nodes with different prompts and contracts, unrelated
to the trial: do not delete or re-time them when changing `backlog`'s planner.

## Unmet criteria (#17, docs/unmet-criteria/)

| Rule | What happens otherwise |
|---|---|
| Every edge out of `coder` and `rework_t1`..`rework_t4` that used to reach `autofix` goes through `task_block_gate` | A stage that blocked would have its empty diff validated and reviewed, and the rework ladder would spend hours on a task no tier can do. Before #17 the coder's `<blocked>` marker was text nothing read, and the coder prompt told it to "implement the closest form" instead, which is how lawncare-saas#2723 shipped a re-check button as its "Resend email" criterion. Covered by the gate tests (`ops/gate_tests/`) (the parsed edges). |
| `task_block_gate` treats a file from an older visit as `none` and deletes it, and treats any other file it cannot read as a valid criterion block as `scope`, never `none`. `next_task` deletes `task_blocked.json` per task | A stale block from an earlier task would stop this one; a malformed block from this visit would let a stage that tried to block reach review. Its two conditional edges also require `outcome=succeeded`: a failed gate applies no context update, and a `none` left by an earlier task would carry an unread block past it. Covered by the gate tests (`ops/gate_tests/`). |
| In `rescue_brief`, `task_block_scope.md` ranks below a failure signature, a final-merge conflict and a final-validation stop, and `partial_remainder` deletes it | A scope note left by an earlier block would name the wrong cause after `[P]`, and would keep `final_stop` from being recognised as the cause. Covered by the gate tests (`ops/gate_tests/`). |
| `return_to_triage` comments first, with `<!-- fabro:triage-questions -->` as the first line, then swaps `agent` and `agent-in-progress` for `needs-info`, and ends the run at `exit` succeeded | Without the marker, issue-triage and arch-review re-triage the issue at once instead of waiting for a human answer. Left on `agent-in-progress`, the scheduler's receipt scan requeues it; ended failed, the requeue rule may put it back in the queue. It writes `stuck_reason.md` before any `gh` call, so its unconditional edge to `mark_stuck` still names the Contradiction. Covered by the gate tests (`ops/gate_tests/`). |
| The node that routes to `return_to_triage` publishes `triage_questions` (`decompose_gate`, `task_block_gate`), on every routing object it prints | The `discord-triage-question` hook fires on `return_to_triage`'s `stage_start`, before that node runs, and reads the key from the run state. A stale key from an earlier visit would send the wrong question. |
| A rework whose findings all need out-of-scope edits completes; only a criterion that cannot be met as written, or a diff too large to keep one, blocks | A `scope` block goes to the rescue gate, so a rework that blocked on scope would skip the stronger tiers the ladder exists to try. |

## Issue selection and queue labels

| Rule | What happens otherwise |
|---|---|
| `backlog` never chooses its own issue: `claim` validates `args.inputs.issue_number` and fails closed | Draft 10 deleted `acquire`, the marker comment and the lowest-ULID arbitration together — the race they patched (two runs implementing jelly-swipe#356 on separate branches) is now prevented upstream, by the scheduler's lease table rather than by the graph. Restoring any selection inside the graph re-opens it. `claim` must keep quitting on an issue that is missing, closed, or not `agent-in-progress` after its idempotent label swap; picking a different issue is the failure the whole design exists to prevent. |
| A Child issue with a predecessor is created `agent-held`, never `agent`, and only the scheduler promotes it | The same-repo saturation race of ADR 0011 D6, one level down: child 2, promoted by a `backlog` run straight from a `main` that lacks child 1, would implement against the wrong tree. `apply_split` creates the first child `agent` and every later child `agent-held`, and no child inherits a queue-state label (`agent`, `agent-in-progress`, `agent-stuck`, `agent-held`, `agent-split`, `agent-remainder`, `agent-noop`, `priority`) from its parent; `agent-held` is invisible to the queue until the scheduler's promoter adds `agent` and `priority` when the predecessor lands. Covered by the gate tests (`ops/gate_tests/`). |
| `apply_split` finds existing children through the sub-issues API, never through issue search | GitHub search is eventually consistent, so a retried split that searched for "already titled" children would miss a just-created child and duplicate it. The sub-issues API is strongly consistent; `apply_split` reuses a child whose title already appears there and links new ones with `POST /issues/{P}/sub_issues`. Its entries are **plain issue objects** (`.number`, `.title`, `.state_reason` at the top level), with no wrapper key: the first build read `.sub_issue.*` in both `apply_split` and the scheduler, and its tests mocked the same wrong shape, so the dedupe never matched and the parent closer always saw an empty list. The read fails closed — an unreadable list read as empty would create every child again — and a failed link POST counts only when a re-read shows the child already linked, because an unlinked child is invisible to both the dedupe and the closer. Covered by the gate tests (`ops/gate_tests/`) and `ops/scheduler/tests/test_split.py`. |
| A Split parent is never labelled `agent` | `backlog` would implement the whole issue, and each child separately. `apply_split` labels the parent `agent-split` and never adds `agent`, so the queue's `agent`-labelled fetch never sees it; the scheduler closes it when every child lands. |
| A `backlog` run implements at most 8 **decomposed** tasks (`tasks_coded`, counted in `improve_gate` on `ready`), and never labels its remainder issue `agent` | Extra-review follow-ups, and slices split from one (`from_extra: true`), are exempt: they never count, are never moved, and are worked in this run, bounded by `extra_prep`'s two-round cap. `next_task` moves every decomposed task past the budget, `decompose` tasks and their split slices, to `remainder.json`, and `file_remainder` files them as one issue labelled `agent-remainder`. The scheduler adds `agent` + `priority` only once the parent PR merges (ADR 0011 D6, `ops/scheduler/src/fabro_scheduler/remainder.py`). Labelling it `agent` at filing time would let the scheduler's same-repo saturation pass start it on the other box, from a `main` without its parent's work. Covered by the gate tests (`ops/gate_tests/`). |

## Opening the PR

| Rule | What happens otherwise |
|---|---|
| `open_pr_prep` refuses to build a PR when the branch tree equals `origin/main` | Nothing downstream of that node reads the working tree: the title comes from the issue title and the body from the first prose paragraph of the issue body, so a branch on which no task landed yields a **well-formed PR asserting the issue was implemented**, and the node's own three `grep -q` assertions pass because they check the derivation, not the diff. The path in is `human_rescue -> [P] Accept partial`, which was written for "some tasks landed, ship what we have" and read identically to "none did". On 2026-09-21 it opened womens-fantasy-sports#1236 and writers-app#949, both 0 files changed; #1236's summary is a sentence lifted verbatim out of issue #1205. The merge phase then made it worse — `review_fix` read the reviewers' "this is empty" verdict and implemented the issue itself, 396/-101 across 4 files. Covered by the gate tests (`ops/gate_tests/`). |
| No agent may edit `.github/workflows/`, and `open_pr_prep` refuses a branch whose commits do | The sandbox pushes over HTTPS with an **OAuth App** token (`gho_`), and GitHub rejects any push whose new commits create or update a workflow file unless that token carries the `workflow` scope. The host token's scopes are `admin:public_key, gist, read:org, repo`, and `repo` does not imply it. Before ADR 0011 D1 the failure was quiet until it was terminal: the post-stage checkpoint push only **warned** (`[git_push_failed]`), so the run continued with the remote branch frozen, and `open_pr` was the first node that cared. Since D1 `backlog` pushes nothing before `open_pr`, so its push is now the first one rejected. Either way `open_pr` — it dies on `git push -u origin HEAD` under `set -e` in ~1s with no routing schema, so the operator sees `unknown error`. Its unconditional edge lands on `human_rescue`, whose `[P] Accept partial` returns to `open_pr_prep` with no attempt counter, so the same deterministic rejection loops. On 2026-09-22 run `01M33SDMZF55NAEV8JV29A8EA4` deleted one clause from a five-line **YAML comment** in womens-fantasy-sports' `test-backend.yml` — seven lines, no workflow semantics, flagged by its own reviewer as a nit — and that single commit rejected 17 of 96 checkpoint pushes, froze the remote branch 3.5h behind the sandbox, and stranded 98 commits and 71 files. The gate walks `git rev-list --no-merges origin/main..HEAD` and reads each commit's own `git diff-tree`, never a two-dot `git diff`: GitHub judges the **commits in the push**, so edit-then-revert is still rejected while a net-diff test would call it clean. Merge commits are skipped, because a run's `git merge origin/main` carries main's workflow changes (issue #18: three runs refused after finishing every task). The same check runs in `integrate` (routed to `rescue_brief` on failure), so the run stops at the end of the offending task, and both messages list only the commit and file that matched. Recovery is to push the branch over **SSH**, which carries no such restriction — once the commits are on the remote, later pushes carry only new commits and are accepted. Covered by the gate tests (`ops/gate_tests/`). |
| The final `git merge origin/main` happens in `final_merge`, never in `open_pr_prep`, and a conflict there goes to `resolve_merge` | `open_pr_prep` used to run it bare under `set -e`. A conflict failed the node with the merge still in the tree. The checkpoint's `git add -A` recorded the conflicted file as resolved and committed the markers as a merge commit. Every later `[P] Accept partial` then found main `Already up to date`, ran CI on the markers, and came back to the gate: wfs#1834 (2026-10-11) and wfs#1747 (run `01M4S16BRA0W1J3W32S6ENJBXH`, 2026-10-12), both after another PR landed the same lines mid-run. `final_merge` aborts the conflicted merge and writes the paths to `/tmp/fabro/final_merge_conflict`. `resolve_merge_gate` reads that file to publish `merge_return=pr` (back to `final_merge`) instead of `task`. `next_task` deletes the file and resets `merge_attempts` on every entry. `open_pr_prep` refuses a branch that *adds* conflict-marker lines, and `rescue_brief` says when landed tasks meet a tree equal to main (main already has the change). Closing the issue stays with the operator. Covered by the gate tests (`ops/gate_tests/`) (real git). |
| A red final validation in `open_pr_prep` routes on `final_route` and never reaches `human_rescue` twice for the same code; the PR never carries edits no reviewer passed when they fail it | Before #35 the node exited 1: the failure was classed `transient_infra`, the gate showed the first 600 bytes of the log (a DOM dump, not a test name), and `[P] Accept partial` went back through `final_merge` to `open_pr_prep` on the same tree, so the run failed identically until someone chose `[X]` and lost the reviewed tasks with it. Run `01M4PP2M37CPE6Q1874V6FBEM5` (lawncare-saas#2733, 2026-10-12): task 2's coder failed, `[P]` shipped its half-built form, and `open_pr_prep` failed on `BusinessDetailsForm.test.tsx` twice with task 1's reviewed work one `[X]` from gone. Now the failing test names go to `final_failures.txt` and the top of `feedback/rework.md`, and the route is, in order: `drop` when `[P]` brought an unfinished task (`partial_remainder` writes `partial_unreviewed`), non-merge commits after `reviewed_sha` (which `integrate` writes) change files, and no PR exists, so `drop_unreviewed` resets to the reviewed work (a reset, never `git restore`, which would revert main's merges in the PR); `draft` when this code already failed here, so `open_pr` opens a draft PR with the tests in the body, `file_remainder` files the rest, and `mark_stuck` posts `draft_reason.md` instead of returning to the gate; `fix` for the run's first red (`final_fix_attempts`, never reset), so `final_fix_prep` appends a `final_fix` task with the merged HEAD as its diff base and `round` 6 and hands it to `rework_t4`, validate and review; and `rescue` for later red on code that has not failed here, with the tests in `final_stop` for `rescue_brief`. "This code" is the patch-id of `git diff origin/main HEAD`, which `fix` and `rescue` add to `final_fail_keys`: a tree key changes whenever main moves during the gate's 4h wait, so the same failing code would return to the gate on every `[P]`. Every edge out of `open_pr_prep` requires `outcome=succeeded`, because a refusal applies no context update and a stale `final_route` must not route it. Guidance after a final-validation stop goes through `final_fix_prep` (`record_guidance` routes on `final_stop`, which `rescue_brief` deletes when another cause outranks it). `partial_remainder` never files a `final_fix` task. Covered by the gate tests (`ops/gate_tests/`) (real git, and the parsed edges). |
| `backlog` does not push checkpoints (`[run.run_branch] push = false`); every push after `open_pr` is an explicit node push, and `open_pr` widens the fetch refspec for the run branch | Fabro's checkpoint commit is always `--allow-empty`, so a per-stage push started a full CI run for every stage once the PR existed (womens-fantasy-sports#1247: 80 commits, 78 Actions runs), and the push after `watch_checks` moved the head CI had passed, so `merge` timed out waiting. Without the refspec, the single-branch clone has no `refs/remotes/origin/<run branch>` and `deliver`'s bare `--force-with-lease` is rejected as `stale info` — it only ever worked because the checkpoint push had already made it a no-op. Covered by the gate tests (`ops/gate_tests/`) (real git). ADR 0011 D1. |
| No `gh` call is left to infer the branch: `gh pr create` passes `--head "$B"`, and `gh pr view` names the branch or a PR number | The sandbox clone is shallow and **single-branch** (`remote.origin.fetch` is `+refs/heads/main:refs/remotes/origin/main`), so `refs/remotes/origin/fabro/run/<id>` can never be stored. `git push -u` still prints `set up to track` and writes the branch config, but `@{u}` fails — and gh resolves the head remote through exactly that ref, so a bare `gh pr create` aborts with `you must first push the current branch to a remote` while the branch sits on the remote at `HEAD`. Cost run `01M2VHAGXNM9JNEY71085HV82Y` its PR on 2026-09-19 after 41 minutes of finished work. `open_pr` is the only node that ever inferred it; `pr-review`'s `claim` meets the same clone property and widens the refspec instead, because `gh pr checkout` needs a real local branch. Finding 11 in `docs/auto-merge/00-overview-and-contracts.md` (removed in `d5cd750`; `git show d5cd750^:docs/auto-merge/00-overview-and-contracts.md`). |

## The rescue gate

| Rule | What happens otherwise |
|---|---|
| Every edge into `human_rescue` passes through `rescue_brief`, and `[P] Accept partial` passes through `partial_remainder` | The gate shows only its fixed label and `response.<last_stage>`, which fabro sets for agent stages alone. `rescue_brief` writes that key and `last_stage` itself, from `failure_signature` and the run's files, so the gate says why the run stopped and what `[P]`, `[X]` and guidance do in that run. Before it, run `01M3Y86Z013N2V1QDNNG591MBQ` showed "Verdict submitted." for a task no agent could finish (a `.github/workflows/` edit). An edge straight to `human_rescue` brings that back silently. `[P]` without `partial_remainder` opens a PR that says `Resolves #N` and records the unfinished task and every unstarted one nowhere; with it they go to `remainder.json` and `file_remainder` files them as one held issue. `rescue_brief` prints only its one-line routing object: fabro scans stdout and stderr together for brace-balanced objects, and echoed finding text could merge with it into an invalid candidate. Its `[P]` and `[X]` texts mirror `open_pr_prep`'s refusals and `mark_stuck`; change them together. Covered by the gate tests (`ops/gate_tests/`). |

## Task validation (ADR 0025)

| Rule | What happens otherwise |
|---|---|
| `validate` routes to `review` only on `outcome=succeeded && context.task_validation_ok=true`, and takes its unconditional edge to `rework_router` on anything else. It writes the placeholder `rework.md` (`## Validation failed (timeout): task validation did not finish`) before it runs anything | A red scoped visit exits 0 and routes by context, so without the context key a scoped failure would take `validate -> review`. A timeout fails the node and applies no context update; a stale `task_validation_ok=true` from an earlier visit would then send it to review, which is why the edge also requires `outcome=succeeded`. The placeholder exists because a timeout reaches `rework_router` with the previous round's feedback still in `/tmp/fabro/feedback/rework.md`. Keep the full path's rework header byte for byte: `## Validation failed (exit N): ./.fabro/setup.sh && ./.fabro/ci.sh` (`rework.md.j2` and the rescue paths match it). A `final_fix` task and every C4 fallback (no task keys, a `full` glob, a deleted non-test file, the index unavailable, a base it cannot diff, an unowned or out-of-cwd selected test, a selection over a target's `max_tests`, a `task-check` error) run the full suite. Covered by the gate tests (`ops/gate_tests/`) (the scoped and full fixtures and the parsed edges). |
| A green `validate` puts back the `rework.md` it found (`/tmp/fabro/rework.prev`), and the routing object is its last command, with `\|\| exit 1` | `rescue_brief` quotes `rework.md` once `round > 0`, so a placeholder left by a passing visit tells the operator a timeout happened that did not. A routing object that fails to print with the node still exiting 0 is `outcome=succeeded` with no update: the stale `task_validation_ok=true` of the last green visit sends a red task to review. Covered by the gate tests (`ops/gate_tests/`) (`tv green restores`, `tv emission failure`). |

## `background.md` (more-local-inference C9, task 08)

| Rule | What happens otherwise |
|---|---|
| `claim`'s `background.md` block (backlog and ralph, an identical R10 copy) never fails the node and never writes to stdout: the `gh api` read is inside an `if`, `jq` ends `|| true`, and an empty file is removed | `claim` runs under `set -e` and routes on stdout. A transient comments read, or a malformed marker, would end every coder run at its first node. |
| `decompose` and both `plan` stages read the background lane's output only through `background.md`, a `required: false` input with an `absent` sentence, never through `issue.json` comments | `issue.json` carries no comments (`gh issue view --json` without `comments`), and a required input would fail every run on an issue with no marker. |
| Each kind keeps its C9 cap in the copy (precheck 1,500, pack 8,000, investigation 2,500), cut with a note | Every `decompose` and `plan` visit pays for the file in hosted credits; an uncapped pack spends what it was built to save. |
